# 我的协作偏好

适用于任何项目。与具体仓库有关的内容放在该仓库自己的技能或文档里。

## 沟通

- **用中文回复**。界面文案、说明、总结都用中文；代码标识符和提交说明沿用项目已有的语言。用户曾明确提醒过这一点。
- **简短、先说结论**。汇报按这个顺序：做了什么、怎么验证的、有什么限制、需要用户决定什么。
- **诚实区分“已验证”和“需真机确认”**。例如无头浏览器里验证了布局，但真机的通知、语音、全屏没验证，就要这样写。
- **做不到的事直接说，并给替代方案**。例如网页没有后台推送，就说明，并给出系统日历导出这个替代办法。

## 什么时候动手，什么时候先问

- 用户说“给些建议”“想想还可以做什么”时，只列建议，**等用户说“可以开始”再实现**。
- 遇到真正的歧义（例如“推送到哪个仓库”），用简短的**选择题**问，把推荐项放第一个；能从上下文推断的就不要问。
- 重大取舍（加后端、改架构、公开仓库）先问；小的实现细节自己决定并说明理由。
- 用户把设计判断交给你时（如“图标看怎样更合适”），给出选择和理由，不要把问题抛回去。

## 质量与验证

- **找根因，不绕过**。偶发的测试失败要查时序或状态原因，而不是重试或放宽断言；放宽超时之前先确认确实是环境慢。
- **用证据证明**。界面问题用截图（手机和桌面各一套）；行为问题用自动化测试；部署后到线上页面复测。
- 修一个问题时，检查同类页面是否有同样问题，一起修。
- 能在目标引擎里复现就去复现（例如用 WebKit 检查 iOS 问题），复现不了就如实说，并给出基于原理的稳妥修法。
- 改完后跑完整测试，不只跑相关用例；更新被改动影响的旧测试和文档。

## 交付

- 用户明确要求推送的仓库，完成后直接提交并推送，随后确认部署成功；**没有授权的仓库不要推送**。
- 提交说明写清楚做了什么。不要提交密钥、令牌和个人数据。
- 临时脚本和调试文件用完就删，不留在仓库里。
- 生成的产物（`dist`、测试结果等）保持被忽略。

## 记录状态

用户希望把“agent 当前状态”也总结下来。长任务结束时写一段状态，包含：

- 最近的提交和部署结果、测试情况。
- 已完成、待用户确认、尚未做的事项。
- 重要的限制和决定（以及原因）。
- 下一步建议。

状态写在对应仓库的技能或文档里，并标注日期，方便下次接着做。

## Windows / PowerShell 环境

- 不要用 `\"` 转义引号，复杂内容用写文件工具或临时 Node 脚本；写文件用无 BOM 的 UTF-8。
- `git push` 的正常输出走 stderr，会被当作错误，以 `git log` 或 CI 结果为准。
- 路径用绝对路径，注意反斜杠。
